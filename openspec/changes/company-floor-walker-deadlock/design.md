# Design: company-floor-walker-deadlock

## Context

`advanceNpcs`（`packages/client/ui-companies/src/client/scene.ts:2361-2493`）推进每个员工的行走。一帧的路径：

```
1. 取当前路点 waypoint = npc.path[npc.pathIndex]        :2378
2. 无路点 → 到达（就座 / 进入功能区停留）                :2379
3. 被让行集合命中则跳过本帧                              :2399
4. 看门狗：time - npc.lastAdvanceAt > 3 → beginWalk 重规划 :2404
5. 计算插值步进 next                                      :2410
6. 若 next 被家具挡住（blockingFixture）→ 绕行分支         :2419
   - ownClear(sidePoint) && ownClear(pastPoint) 均通过 → 采用绕行 :2447
        npc.path = [...detour, ...npc.path.slice(npc.pathIndex)]
        npc.pathIndex = 0
        npc.blockedSteps = 0
        npc.lastAdvanceAt = time                          :2449
   - 找不到可用绕行 → blockedSteps += 1；≥4 时垂直退避或重规划 :2451
7. 未被挡 → 实际位移，blockedSteps = 0，lastAdvanceAt = time
```

三个设计缺陷叠加成死循环：

- **`ownClear` 只判断端点**（`blockingFixture(spot) === undefined`，:2423）而不判断"当前位置 → 该端点"这一段是否可通行。端点空旷但进入段被挡时，绕行被误判为可行。
- **绕行分支刷新 `lastAdvanceAt = time`**（:2449）。看门狗（:2404）本意是"3 秒没前进就重规划"，却被这个"没有任何位移"的分支每帧满足，永不触发。
- **绕行分支重置 `blockedSteps = 0`**（:2448）。放弃/退避分支（:2451 起）因此永远到不了，暴怒与破坏逻辑（:2472）也连带失效。

`beginWalk`（:2282-2329）本身按段构造 2-5 个点，无累积来源；增长完全来自第 6 步的 prepend。

## Goals / Non-Goals

**Goals:**

- 行走员工满足"推进或重规划"，消除"位置冻结 + 路径无界增长"这一稳定失败态。
- 修正后不改变正常行走手感（速度、路径形态、让行、到访上报、就座/亮屏）。

**Non-Goals:**

- 不重做寻路（不引入全局 A*/导航网格）；仍沿用现有"沿轴走廊 + 绕行点"的局部策略。
- 不改 `beginWalk` 的路径形态与门洞/走廊几何。
- 不改 mood/damage/让行 的既有语义，只在阻塞计数变得更真实后让它们按原设计生效。
- 不动服务端、协议、数据面。

## Decisions

### D1: 绕行可行性按"完整移动段"校验，而非端点

采用绕行的前提改为：**当前位置到 sidePoint、以及 sidePoint 到 pastPoint 两段都无阻挡**。实现上可对段做采样点校验（按 NPC 半径的步长），或复用注册表的线段查询（若已有）。备选：只多校验一个中点——治标不彻底，长段仍可能穿过障碍，否决。

### D2: 看门狗以"实际位移"为准

只有在**真的改变了 `person.position`** 的分支才刷新 `lastAdvanceAt`。绕行分支不产生位移，因此不得刷新。这样 3 秒停滞必然触发 `beginWalk` 重规划（:2404 既有逻辑即可生效，无需新机制）。备选：给绕行分支单独计一个"绕行次数"阈值——与 D3 的 blockedSteps 语义重复，否决。

### D3: 绕行尝试计入阻塞，使放弃分支可达

"判定为可行却仍未位移"的一帧应 `blockedSteps += 1` 而不是重置为 0。这样既有的"≥4 次阻塞 → 垂直退避 / 重规划"（:2451-2470）恢复可达，暴怒与破坏（:2472）也随之按原设计工作。这同时给路径增长设了上界：绕行前置最多发生到阈值次。

### D4: 保持局部策略，不引入全局寻路

三处缺陷是判定与记账错误，不是策略能力不足；修正后局部绕行足以覆盖既有布局（走廊 + 门洞 + 家具）。引入导航网格是重写，超出本缺陷范围。

### D5: `beginWalk` 用房间真实足迹判定「在房内」，并自校验路径

D1-D3 只止住了路径无界增长，却暴露第二个叠加缺陷：`inRoom` 原用「到工位距离 < `ROOM_D/2 + 1`（半径 6）」判定，把站在 CEO 南墙门外走廊的员工误判为「已在房内」，于是生成一条穿过南墙的直线；路径被挡后进入有界震荡，**永远到不了工位**。修复：

1. `inRoom` 改为房间足迹（`|Δx| ≤ ROOM_W/2 && |Δz| ≤ ROOM_D/2`）。
2. `beginWalk` 生成路径后用 `segmentBlockingFixture` 逐段自校验；任一段被挡则改走门洞。

### D6: 路由按「房内/房外」分侧分发，去工位不再有逆向段

第一版门洞兜底 `enterViaDoor` 无条件先走 `(from.x, hallZ)`，对**已在房内**的员工等于先送回走廊再重新进房；且「去工位」尾部又 `append(target.x, hallZ)`，把它从工位再次送回走廊。两者叠加，配合 `updateBusy` 的频繁重规划，形成「门口来回震荡」。修复为四条单调路线——`insideToDesk` / `outsideToDesk` / `insideToOutside` / `outsideToTarget`——每侧都只朝目标推进，去工位直接落到 `target`。

### D7: `updateBusy` 不在员工已在途中时重置路径

忙碌翻转经频繁渲染触发，原实现每次 `busy` 都调 `beginWalk`，把一个正在走向工位的员工重置回当前点。改为：已 `sit` 则直接亮屏；`destination === 'desk'` 则保持当前路径；只有「非坐且未朝工位」才起步。

## Risks / Trade-offs

- [段校验比端点校验更严格，可能出现"原本能绕过去的窄缝现在绕过不去了"] → 更严格是正确方向（原行为会穿模或原地卡死）；若窄缝真实可通，采样步长取 NPC 半径量级即可通过。实现时对现有布局做一次人工走查。
- [D3 让阻塞计数变真实，短时间可能出现更多暴怒/破坏，视觉上与以往不同] → 属恢复设计意图（原逻辑形同虚设）；如手感过烈，调阈值而非回退记账。
- [修复后既有 3D 单测/快照若断言了旧路径长度或旧 blockedSteps 会失败] → 属预期差异，随实现更新；不得用放宽断言来通过。
- [房间足迹判定（D5）对「门洞内」的过渡位置仍可能判为房内] → 路径自校验兜底：即使足迹判定偏差，被挡段仍会改走门洞，不会穿墙。

## Migration Plan

纯客户端行为修复，无数据迁移。合并后刷新页面即生效。回滚 = 回退提交。

## Open Questions

- 段校验的实现细节（离散采样 vs 线段—AABB 求交）：取决于注册表现有能力，实现时择一，不改变规格。
- 是否需要给路径长度加一个硬上限作为纵深防御（即便记账修好）——可在实现时按收益决定。
