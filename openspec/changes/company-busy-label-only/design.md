# company-busy-label-only — 设计

## Context

「在忙」的信号源已经正确且无需改动：宿主 `company-management.busyVerdict` 按员工名下会话（含群会话的成员会话，经审计归属）的 `agent.status === 'running'` 判定，客户端再以实时 `runningSessions` 镜像覆盖 5 秒轮询值。实测一条群内提及：回合期间 `member.running=true`、floor `busy=chat`，回合结束随即翻回。问题不在判定，而在三维场景把同一状态同时用作了**呈现**与**行为驱动**。

场景内 `npc.busy` 现有四处耦合（均在 `packages/client/ui-companies/src/client/scene.ts`）：

- `advanceNpcs` 中，走动中的忙碌小人被强制改道回工位（`if (npc.busy && npc.destination !== 'desk') beginWalk(npc, 'desk')`）；
- `advanceNpcs` 中，就座小人仅在空闲时才允许发起新游走（`if (!npc.busy && time >= npc.nextDecisionAt)`）；
- `advanceNpcs` 的功能区停留分支中，忙碌小人被禁止结束停留（`if (npc.busy) continue`）；
- `updateBusy` 中，翻转为在忙时若未在去工位路上则立即改道回工位，且空闲翻转把 `nextDecisionAt` 归零使其立刻可再出门。

尺度不匹配由此产生：一次会话回合常在数秒内结束，而经走廊走回工位需要更久，于是归位被反复打断、空闲随即再出门，观感为"标着在忙的小人一直到处跑"。

## Goals / Non-Goals

**Goals:**

- 「在忙」只作用于头顶标签；小人的位移行为与忙碌状态无关。
- 保留就座时的工作呈现（桌面亮屏、打字动画），因为它本就只在就座时生效，不引入"必须归位"的要求。

**Non-Goals:**

- 不改动宿主忙碌判定、客户端实时镜像、以及单聊/群聊的忙碌语义。
- 不改动园区（外部）与公司卡片的「在忙 N」汇总——它们本就是纯数字标记。
- 不新增"忙碌时禁止游走"的限制（即不选把忙碌作为移动门禁的另一方向）。

## Decisions

### 1. 彻底解耦：忙碌不是移动的输入

删除上述四处耦合，使忙碌小人的游走节拍与空闲员工完全一致。理由：用户的要求是"头顶显示忙碌即可，不需要一定要回到工位上"——这是**撤除一项义务**，而非新增一项限制。彻底解耦是满足该语义的最小且唯一自洽的实现；任何保留部分耦合的做法（如"忙碌时不许新出门"）都会重新引入一条"忙碌改变移动"的规则，与本需求相悖，并会连带产生"忙碌小人卡在茶水间不动"的新观感问题。

**备选**：保留游走门禁、仅删除强制归位。否决：会使忙碌且就座的小人永不出门、忙碌且在功能区的小人被 `if (npc.busy) continue` 钉在原地（停留在原地的"在忙"看起来更像卡住），且仍需维护四处的门禁逻辑。

**备选**：保留强制归位但加"最短驻留"缓冲。否决：只是掩盖尺度不匹配，小人仍会为忙碌走回工位，与用户明确表达的"不需要回到工位"直接冲突。

### 2. 亮屏与工作动画降为"就座伴随表现"

桌面屏幕的点亮本就只在两种时机发生：到达工位时（`if (!toDesk) setScreen(npc, false)` 反向，及到达后 `setScreen(npc, npc.busy)`），以及 `updateBusy` 中"已就座"分支。解耦后这两处无需改动，只是语义上从"在忙的一种呈现"变为"在忙且就座时的伴随呈现"。未就座的忙碌员工只显示头顶标签、屏幕熄灭——这正是"头顶显示即可"的直译。

**备选**：让未就座的忙碌员工也远程点亮其工位屏幕。否决：视觉上会出现"空工位亮屏"，反而暗示有人在场，语义更差。

### 3. 宿主与线协议不动

忙碌判定已满足需求（单聊会话、群会话成员会话、自主任务均覆盖），改动它只会扩大范围并触及已归档的群会话/任务播报契约。本变更严格限于客户端呈现层。

## Risks / Trade-offs

- **[忙碌员工可能在整段工作中一直游走、屏幕多为熄灭]** → 这是本需求选择的语义（`在忙` ≠ 必须坐在工位）；用户明确接受"头顶显示忙碌即可"。若日后希望"在忙即坐班"，那是相反方向的另一变更，需重新引入归位并解决尺度不匹配。
- **[子代理/成员会话的 running 位是否总能到客户端]** → 本次实测已证实群成员会话的 `running` 能经 `host/session-status` 帧到达客户端并驱动 floor busy，故无新风险；改动不触碰该链路。
- **[忙碌与空闲切换时 `updateBusy` 的 `nextDecisionAt = 0`]** → 解耦后该归零只影响空闲恢复的即时性，不再与归位冲突；保留现状即可，无需额外改动。
