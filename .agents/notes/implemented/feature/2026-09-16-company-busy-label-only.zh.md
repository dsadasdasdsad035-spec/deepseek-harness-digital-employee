# Agent Note: 公司楼层「在忙」只是标签，不驱动移动

Status: implemented

[English](2026-09-16-company-busy-label-only.md) | 中文

## Problem

办公楼层把同一个员工状态——「在忙」——同时用于两件无关的事：绘制头顶 `在忙`/`空闲` 标签，以及操控小人身体。四处耦合让忙碌成了移动输入：忙碌的行走者被强制改道回工位；就座的忙碌成员被禁止发起行程；忙碌成员被禁止结束功能区停留；忙碌翻转还会重发一次回工位路线。两个角色在时间尺度上冲突：一次会话回合（群里一次提及、单聊一句短回复）两三秒就结束，而按门洞规划走回工位要好几秒。于是回家路被回合结束打断，空闲翻转后成员立刻重新决策（`updateBusy` 把 `nextDecisionAt` 归零），观感就成了「标着在忙的成员一直在到处跑」。

## Decision

- **忙碌只驱动呈现。** 四处耦合全部移除。成员转忙时行程不再被取消，就座成员无论忙闲都照样决定是否出门，功能区成员无论忙闲都照样结束停留。因此忙碌成员与空闲成员以完全相同的节拍游走。
- **标签与位置无关。** 无论就座、走在走廊还是停留在功能区，忙碌都显示在头顶标签上。桌面屏幕与打字动画保留，但仅在就座时生效；离开工位的忙碌成员只显示标签、屏幕熄灭，而不是在空椅子上方远程亮起一盏「有人在此」的灯。
- **决策接缝是纯函数。** 就座的「出门 vs 等待」判断抽为导出的 `seatedIdleDecision({ time, nextDecisionAt, amenityCount, leaveRoll, pickRoll, waitRoll })`。忙碌被刻意排除在其输入之外，于是「忙碌永不门禁游走」成为签名的性质、而非下一位编辑必须记住的约定——与既有的 `resolveBlockedStep`（行走者受阻帧逻辑）抽法一致。
- **忙碌信号本身不变。** `company-management.busyVerdict` 已经把成员自身会话的 agent 视为运行中，单聊与群提及皆然（群场景经成员会话的审计记录归属），客户端以实时 `host/session-status` 运行位覆盖 5 秒楼层轮询。已实测：一条群提及在 1 秒内令 `member.running=true`、楼层 `busy=chat`。宿主侧与线协议均无改动。

## Alternatives considered

**保留回家、加最短就座驻留。** 否决：只掩盖尺度不匹配，且保留了用户明确排除的行为——「根本不需要回到工位」。成员仍会为一次忙碌翻转离开行程。

**只删强制回家、保留其余门禁。** 否决：会留下「忙碌的就座成员永不出门」与「忙碌成员被 `if (npc.busy) continue` 钉死在功能区」——一个「在忙」却僵住的形象读起来像故障，且三处忙碌门禁仍需维护。

**让任何位置的忙碌成员都点亮其工位屏幕。** 否决：空椅子上方亮屏暗示有人在场，反而混淆楼层的读法。

## Consequences

- 在群聊或单聊中确实在工作的成员，无论站在哪里都头顶 `在忙`、并保持当前路线；楼层不再产生「在忙却四处乱窜」的观感。
- 楼层放弃了那个从未被规格化过的暗示：在忙就等于「坐在工位」。这正是用户选择的取舍：标签即忙碌在楼层可见效果的全部。
- 纯函数接缝增加了一小块可测面；移除的四处耦合删掉的代码多于抽出所增。
- 不涉及模型可见路径、会话事件、快照或 SDK 投影——纯粹是客户端的三维呈现。

## Testing

- `packages/client/ui-companies/tests/entity-registry.client.spec.ts` 新增 `seated idle decision` 块：合格且在阈值下的抽取命中时出门、超阈值时等待并顺延、未合格时等待、无功能区时拒绝出门、pick 抽取为 1 时钳到最后一个功能区。忙碌不是参数，故任何用例都不可能断言它门禁该选择。
- 重建后的 3080 浏览器实测：一条群提及把成员头顶标签翻为 `在忙`，成员保持当前行程而不改道回家；回合结束翻回 `空闲` 并恢复既有游走。
