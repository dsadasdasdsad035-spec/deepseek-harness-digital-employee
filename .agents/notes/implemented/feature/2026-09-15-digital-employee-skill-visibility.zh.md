# Agent Note: 数字员工的技能到达模型

Status: implemented

[English](2026-09-15-digital-employee-skill-visibility.md) | 中文

## Problem

数字员工的模板会声明 `capabilities.skills`，员工组装也把技能注册表收窄到该集合，但模型从来收不到这份清单。技能进入模型视野的唯一通道是技能能力缝的目录，它由 `tool-skill` 消费者发布，并以「调用方 agent 解析到的正是该消费者注册的加载器工具」为门：消费者读取 `ctx.tools.get('skill', agent) === skillTool`，命中才做技能快照，否则发布空目录。

员工组装紧接着把工具收窄到声明的业务工具，`skill` 不在其中，该判定失败、目录恒空。实机测试把后果坐实：一个声明漫画技能的实例自称项目经理、报出 PMP/WBS 等能力，因为它报的「技能」是从指令文本幻觉出来的，而不是读自目录。第二处成因叠加其上：部分员工 preset（如 `project-manager-test`）挂了技能定义却没挂目录/加载器消费者，这类员工即使不被限制也无目录。

对照之下，工具是真实隔离的（一方调用 `project_board` 拿到真实数据，另一方回答「我没有这个工具」），正是这一点让技能缺口凸显。

## Decision

- **让技能加载器穿过业务工具限制保持可见。** 员工组装现在为每个声明了技能的员工把技能缝的加载器工具名加进工具白名单。名字由技能缝拥有（`SKILL_LOADER_TOOL_NAME`），消费者不硬编码 `skill`；加载器可见后目录即已正确，因为内容由 `skills.restrict({ allow: authority.skills })` 决定。
- **声明技能却无加载器的 preset 组合期失败。** 通过 agent 的工具视图解析加载器，意味着 preset 缺消费者的员工会在组合期失败并给出指明缺失插件的诊断，而不是组装出一个模型看不到其技能的员工。
- **不动技能缝的可见性门，也不把技能渲染进系统提示。** 保留该门使目录与加载器同生共死（不会出现「列得出但加载不了」的清单，加载器被有意拒绝时也不泄漏技能名）。把技能渲染成提示段会重复目录的投影逻辑并丢掉按需加载。两种备选均否决。
- 专家组合沿用同一加载器保留逻辑，因此授权了技能的委派专家也能看到自己的目录。

## Alternatives considered

- **把 `authority.skills` 渲染成系统提示段**（像 identity/personality）——重复目录逻辑、丢掉技能正文的按需加载，且技能变更时多一处需同步。
- **让目录独立于加载器可见性**——破坏技能缝「列出与加载一起发布」的既有契约，且在加载器被有意拒绝时有泄漏技能名的风险。
- **容忍声明技能却无加载器的 preset**——这正是本次要修的静默失败。

## Consequences

端到端验证通过。keyless 组装快照（`project-manager-digital-employee`）现在断言一条持久 `skill-catalog` 消息，其条目等于员工的授权技能，且 `visibleTools` 多出了 `skill`；注册表/目录断言走 `createTask`，与单聊和群成员是同一条路径。包级测试覆盖：加载器穿过限制保留、缺加载器时组合失败、未声明技能时不加加载器。对真实服务验证时，群成员会话的 `skill-catalog` 消息恰好是 `project-planning, risk-review, status-reporting`（授权集合），员工也只回这几个名字，不再单凭指令文本作答。

仍有一处数据层发现未在此修复：实例的模板指令写着「项目经理」而声明的技能是漫画/视频时，模型报的是指令中的角色——因为冲突时模型更看重指令。这是脏 fixture 数据（模板/实例错配），不是代码缺陷；理顺这类实例属运维工作。

## Problem space left open

- 是否该在 preset 编写/挂载时就校验「声明技能必有加载器」，而不是等到首次员工组合——挂载期检查能更早失败。
- 上述脏数据错配提示了一个未来校验：当模板声明的技能与其指令文本不一致时给出告警。
