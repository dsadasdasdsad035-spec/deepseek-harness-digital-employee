# Agent Note: 数字员工记忆接线

Status: implemented

[English](2026-09-16-digital-employee-memory-wiring.md) | 中文

## 问题

数字员工记忆已经有完整的存储与策略层（SQLite provider、受控提升、有界检索），却没有生产路径：模型没有记忆工具，员工在任何回合里都无法保存或回忆任何东西；两个聊天入口创建任务会话时也不传记忆查询，导致连种子记忆都到不了提示词。该能力只存在于测试驱动里——这正是纯存储层变更无法补上的缺口。

## 决策

员工组装为每个员工挂载一个作用域本地工具 `employee_memory`。`save` 以会话来源（`employee-memory-tool`，`sensitive: false`——敏感性始终是 provider 策略，绝不是模型输入）构造候选，并流经既有的 `digitalEmployeeAgent.promoteMemory`，因此预览会话、决定日志与策略执行走的就是生产代码路径，而不是并行实现。`search` 在与任务投影相同的评分下查询该员工自己的记录，limit 默认 5、硬上限 20。工具注册在 agent 作用域内，而工具注册表刻意把作用域本地名称排除在 `tools.restrict()` 校验之外——作用域本地名称不可被限制——因此它按契约在业务工具限制之后保持模型可见，而不需要加白名单。

两个线上聊天入口现在都传有界查询：空文本取最近的长期记忆（字面评分下用户消息原文几乎不可能命中；空文本按最近优先投影全部记忆）。上限是每个入口各自的校验配置字段（`memoryProjectionLimit`、`memberMemoryProjectionLimit`；默认 5，范围 1–50），不是硬编码常量。`resumeTask` 增加同样的可选查询，且只有群聊冷恢复路径传入，headless 的 resume 调用方行为不变。

project-manager 组装快照端到端演练该工具：driver 通过工具保存一条记忆，期望 transcript 钉住 `visibleTools` 中的该工具、以及带会话日志决定事件的接受决定。验收行记录 `memoryIdAssigned` 而非 UUID，保持 transcript 确定性。

## 已考虑的替代方案

- **按模板权限 gate 该工具**：记忆是员工概念的内在能力，策略层已治理写入，加 gate 会在无迁移的情况下静默禁用既有模板的保存。
- **用用户消息做匹配投影**：字面评分下实践中几乎投影不出任何东西；最近 N 条是确定性、有界的，检索升级后在相同请求形状后替换排序策略即可。
- **resume 一律重投影**：会改变所有既有 resume 调用方（headless runner），而只有群聊冷恢复路径需要它。

## 后果

记忆有了完整的线上环路：聊天入口投影进来，模型可在回合中保存与检索，决定落会话日志，冷恢复的群会话能看到当前记忆。策略失败作为工具结果呈现给模型，而不是静默丢弃。空文本投影是已知的粗糙边——重近因轻相关性——检索升级应在不变的请求形状后替换查询策略。
