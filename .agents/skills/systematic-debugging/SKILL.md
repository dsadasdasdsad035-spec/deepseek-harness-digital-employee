# 系统化调试

## 概述

随机修复浪费时间并产生新 bug。快速补丁掩盖根本问题。

**核心原则：** 在尝试修复之前，始终找到根本原因。症状修复是失败。

## 铁律

```
没有根本原因调查，就没有修复
```

如果你没有完成第一阶段，你不能提出修复方案。

## 四个阶段

### 第一阶段：根本原因调查

**在尝试任何修复之前：**

1. **仔细阅读错误消息** — 不要跳过错误或警告，完整阅读堆栈跟踪
2. **稳定复现** — 能可靠触发吗？确切步骤是什么？
3. **检查最近变更** — git diff、最近提交、新依赖、配置变更
4. **在多组件系统中收集证据** — 在每个组件边界添加诊断工具，运行一次收集证据，然后分析
5. **追踪数据流** — 坏值从哪里来？什么调用了它？一直追溯到源头

### 第二阶段：模式分析

1. **找到有效示例** — 在同一代码库中找到类似的有效代码
2. **与参考对比** — 完整阅读参考实现，不要略读
3. **识别差异** — 列出有效和无效之间的每个差异
4. **理解依赖** — 这需要什么其他组件？

### 第三阶段：假设与测试

1. **形成单一假设** — 明确陈述："我认为 X 是根本原因，因为 Y"
2. **最小化测试** — 做最小可能的变更来测试假设
3. **验证后继续** — 有效？进入第四阶段。无效？形成新假设。不要叠加更多修复。

### 第四阶段：实现

1. **创建失败测试用例** — 最简单的复现，如果可能用自动化测试
2. **实现单一修复** — 解决已识别的根本原因，每次一个变更
3. **验证修复** — 测试通过了吗？没有其他测试被破坏？
4. **如果修复无效** — 停止。尝试了几次修复？如果 ≥ 3 次：**停止并质疑架构**

## 常见合理化借口

| 借口 | 现实 |
|------|------|
| "问题很简单，不需要流程" | 简单问题也有根本原因。流程对简单 bug 很快。 |
| "紧急情况，没时间走流程" | 系统化调试比猜测-检查的折腾更快。 |
| "先试试这个，然后再调查" | 第一次修复设定了模式。从一开始就做对。 |
| "我看到问题了，让我修复它" | 看到症状 ≠ 理解根本原因。 |
| "再试一次修复"（已失败 2+ 次后） | 3+ 次失败 = 架构问题。质疑模式，不要再修复。 |

## 警示信号 — 停止并遵循流程

- "先快速修复，之后再调查"
- "只是改变 X 看看是否有效"
- "一次添加多个变更，运行测试"
- "我不完全理解但这可能有效"
- "再试一次修复"（已尝试 2+ 次）
- 每次修复都在不同地方暴露新问题

**所有这些都意味着：停止。回到第一阶段。**
