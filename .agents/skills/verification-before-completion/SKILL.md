# 完成前验证

## 概述

在没有验证的情况下声称工作完成是不诚实，而不是高效。

**核心原则：** 始终先有证据，再做声明。

## 铁律

```
没有新鲜的验证证据，就没有完成声明
```

如果你在这条消息中没有运行验证命令，你不能声称它通过了。

## 门控函数

```
在声明任何状态或表达满意之前：

1. 识别：什么命令能证明这个声明？
2. 运行：执行完整命令（新鲜、完整）
3. 阅读：完整输出，检查退出码，计算失败数
4. 验证：输出是否确认声明？
   - 如果否：陈述实际状态并附证据
   - 如果是：陈述声明并附证据
5. 只有这样：才能做出声明

跳过任何步骤 = 撒谎，而不是验证
```

## 常见失败

| 声明 | 需要 | 不够 |
|------|------|------|
| 测试通过 | 测试命令输出：0 个失败 | 之前的运行，"应该通过" |
| 构建成功 | 构建命令：退出 0 | lint 通过，日志看起来不错 |
| Bug 已修复 | 测试原始症状：通过 | 代码已更改，假设已修复 |
| 需求已满足 | 逐行检查清单 | 测试通过 |

## 警示信号 — 停止

- 使用"应该"、"可能"、"似乎"
- 在验证之前表达满意（"太好了！"、"完美！"、"完成！"等）
- 即将提交/推送/PR 而没有验证
- 信任代理的成功报告
- **任何暗示成功而没有运行验证的措辞**

## 合理化预防

| 借口 | 现实 |
|------|------|
| "现在应该可以了" | 运行验证 |
| "我很有信心" | 信心 ≠ 证据 |
| "就这一次" | 没有例外 |
| "代理说成功了" | 独立验证 |
| "部分检查就够了" | 部分什么都证明不了 |

## 底线

**验证没有捷径。**

运行命令。阅读输出。然后声明结果。

这是不可协商的。
